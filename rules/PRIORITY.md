# Priority and inheritance

Runtime inheritance aliases (inject before execution): Engineering Constitution = AGENTS.md + rules/PRIORITY.md + rules/SECURITY.md + rules/REPORTING.md; Development LOOP = docs/harness/v3/CONTROL_FLOW.md + policy/transitions.json; Security Rules = rules/SECURITY.md. These are explicit v3 bindings for the preserved role texts, not missing v2 files. The runtime loads and hashes these segments, with Valera's role prohibition taking priority over generic engineering duties.

Runtime policy is outside model authority. Host instructions and the user's actual authorization govern the session. Project safety invariants and explicit role prohibitions restrict generic role duties; required checks come from policy/checks.json plus task acceptance. Skills are procedures, not permissions.

Original agent bodies in agents/ are preserved and hash-checked. Their generic INSPECT/RESEARCH/EXECUTE instructions mean delegation for Valera, as its existing overlay states. Skills/instructions are separate context segments loaded by the runtime. Do not append shared engineering text after Valera's overlay without testing the effective prompt.

Historical v2 is an immutable source snapshot, not an additional active policy engine. Exported v3 rules replace v2 lifecycle interpretation. LOOP phase mapping: RESEARCH=CLASSIFIED/PLANNED; PLAN=PLANNED/ASSIGNED; EXECUTE=EXECUTING; REVIEW=REVIEWING; VERIFY=VERIFYING/COMPLETION_AUDITING/REREVIEW; SHIP=ACCEPTED/DONE. SHIP never implies deploy.

When a role prompt conflicts with policy, stop the conflicting operation and report the exact rules to Valera. Do not silently merge requirements or pick the least restrictive rule. User-approved scope changes require task revision and re-verification; cannot overwrite the historical contract.
