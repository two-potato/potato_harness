# Durable core (single host)

These are host-owned Python interfaces, not worker tools. The controller DB must already be initialized with migration 1; owned supplementary tables are created without modifying that migration. The host must retain database, role/rule sources, callbacks and effect credentials outside worker access.

- `Outbox(database).reserve(task_id, revision, action, key, approval_id=None)` persists canonical JSON and returns an effect ID. Reusing a key with changed task/action/approval fails. `claim(effect_id)` atomically claims PENDING once **only while the authoritative task is in EXECUTING**; merely reserving a PENDING effect in an earlier state grants no dispatch right. This guard is necessary, not sufficient: the trusted host must separately authenticate worker grants/lease/budget and authorizations for the actual side effect. `finish(effect_id, result, success)` resolves DISPATCHING. `mark_unknown(effect_id)` marks uncertain dispatch. `reconcile(effect_id, result, success)` is only for host-confirmed UNKNOWN outcomes. Identical final receipts are idempotent. `unresolved(task_id)` lists PENDING, DISPATCHING and UNKNOWN; cancellation must check those states within its own state-write transaction. No network execution or automatic replay exists. Approval rows alone do not authenticate issuers; host authorization must validate issuer credentials and revocation immediately before effects.
- `Budget(database).configure(task_id, record)` validates schema, finite values, task/budget/revision bindings and soft <= hard. Existing configuration is immutable. `reserve(task_id, tokens, cost_usd, attempt_id)` serializes hard token/cost, wall time and parallel limits, returning a durable receipt. Unknown cost, NaN and infinity fail. `settle(attempt_id, used_tokens, used_cost)` releases reservations once and stores actual usage even when actual usage exceeds the estimate; exhausted limits deny subsequent work. Repeated identical settlements succeed, substituted ones fail. Time starts at first reservation, uses the host clock and includes intervening waits. The host must separately implement approval-wait exclusion and repair/no-progress policy; no claim is made that this component accounts those periods. Soft limits are recorded policy, not enforced dispatch stops.
- `Scheduler(database, dependency_verified=host_callback, max_ready=64).ready(dag)` returns a bounded stable list, not leases or dispatch authorization. Every node references an actual current task; duplicate nodes/tasks/edges, missing dependencies, cycles and differing task `depends_on` fail. Only PLANNED/REPAIR can be ready. Each predecessor must be DONE, have exact-current-revision/target evidence, a hash-valid immutable publication and a literal `True` from the trusted dependency callback (default deny). Publication may precede pinning by one revision. Callback must validate attestation provenance and link publication to the target. Cancelled/blocked predecessors never silently satisfy dependencies. This is not a fairness implementation.
- `compile_context(task, recipient, segments, limit, token_count)` accepts recipient `{role, session_id}` and segments `{name,text,mandatory,trust}`. It loads host repository role and fixed rules, hashes their exact content, redacts common secret patterns, encodes caller segments as inert JSON data regardless of requested trust, and uses the injected real host tokenizer on the final serialized prompt. Mandatory overflow fails; optional whole segments are admitted in input order when they fit. Unknown/unassigned roles fail (QA/security/coordinator recipients are allowed). The returned runtime envelope includes `text`, `token_count` and schema context fields; remove those two runtime fields before validating `schemas/context-pack.schema.json`. JSON delimiting is a boundary representation, not a claim that a model is immune to prompt injection. Configure recipient access on the host; a caller-supplied role is not an authenticated identity. Tokenizer correctness belongs to the host.

Verification: `python -m unittest tests.runtime.test_durable_core -v` tests effect identity/uncertainty, process claim contention, process budget contention, unknown/nonfinite costs, actual overrun, receipt substitution, time/parallel limits, invalid dependency graphs, context limits/redaction and combined context/reservation/effect accounting. These tests provide no live-provider or container-isolation evidence.
