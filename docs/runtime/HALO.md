# Offline HALO proposal engine

Run the self-contained synthetic benchmark from the repository root:

```sh
python -m harness.halo --output /tmp/new-halo-demo
```

The output directory must not exist. The command writes `proposal.json`, `evaluation.json`, and a separate durable `ledger.sqlite`; exit 0 means PROPOSED, never approved. It uses no provider or network. Trace text, policy and dataset labels are explicitly synthetic demo values, not measured production results. The baseline SHA is read from the actual repository HEAD without modifying Git; dirty working tree contents are not attested by that SHA. Production 3.3 activation remains unproven.

`run_demo(Path) -> dict` is the reference workflow. `optimize(host, current_baseline, train, evaluation, evaluator, ledger, attempt_id, candidate_spec=None)` accepts already redacted structured optimizer traces. A trusted host supplies immutable baseline/policy, three distinct version IDs and content digests, independent optimizer/evaluator identities, and an evaluator code digest. The host must obtain the current baseline from its trusted repository snapshot immediately before execution; a model-supplied current baseline is not freshness evidence. Recheck freshness again before any later application.

The candidate domain contains exactly four optional detail character limits: 0, 64, 128, 256. Candidates have one permitted key. Unknown keys, alternate limits and boolean limits are rejected. Mandatory `trace_id`, `status`, `checks` and `bindings` pass through unchanged. This engine cannot modify policy, role prompts, checks or evaluator source. Inputs must contain only the five specified fields; redaction is the upstream trusted host's responsibility. Optional details must truly be optional for the consuming application; this microbenchmark does not establish semantic utility of arbitrary removed prose.

Train selects a candidate; evaluation and holdout compare the same before/after rows with the same deterministic evaluator. The independent evaluator retains holdout examples and releases aggregates only. It verifies its dataset digest, code digest and holdout ID disjointness against optimizer-visible IDs. The host and evaluator are trusted. The reference implementation uses Python object encapsulation and identity checks, **not OS isolation**: malicious Python in the same process can inspect private fields or monkeypatch code. Deployment must place the optimizer in a restricted process and authenticate the evaluator/host interface. No holdout examples, evaluator credentials or evaluator source are returned by the optimizer interface.

Metrics are actual sample counts and sums of optional text characters, not token usage, paid cost, latency or quality estimates. Each retained mandatory field is compared for regressions. A proposal requires zero observed regressions and savings of at least 32 characters and 5% on both evaluation and holdout. Small/noisy inputs produce HOLD; empty input is rejected or held without invented sample sizes. Results do not claim statistical significance or mathematical safety. No stochastic model is used, so randomized execution order has no effect on this character-count benchmark. A future stochastic evaluator needs paired randomized runs, at least three repeats and reported uncertainty.

The independent SQLite ledger uses `BEGIN IMMEDIATE` to reserve before validation or evaluation. All accepted reservations consume one of ten attempts per holdout content digest, including invalid candidates, evaluator failures and rejects. All domain candidates are searched on train only; one selected candidate consumes the reserved holdout attempt. Duplicate attempts return UNKNOWN and are never resent, including after a crash or restart. Completed results remain inspectable in the ledger. Version IDs are pinned to content digests transactionally. Relabeling identical holdout content shares the same ten-attempt budget and duplicate-attempt identity; assigning different content to an existing version is rejected. Legacy ledgers with unbound historical attempts fail closed and require trusted migration. Blank attempt IDs are rejected before reservation; proposals are schema-validated before return. After ten reservations, the content is held for trusted rotation/quarantine. Ledger ownership, backups, host version registration and authenticating new holdout content are deployment responsibilities; this API is not a hostile-client authorization boundary. Do not replace the ledger between sessions to reset the cap.

`TrustedEvaluator` implements the reference aggregate callable; `Host`, `Candidate`, and `Ledger` provide the other public interfaces. Records with metrics conform to `schemas/halo-proposal.schema.json`; an early failure returns a diagnostic status without fabricating a proposal. The only output statuses are PROPOSED, HOLD, REJECTED and UNKNOWN (duplicate reservation). Human review and rollback remain separate, and there is no apply, approval or merge operation.

Tests: `.venv-demo/bin/python -m unittest tests.runtime.test_halo`. They cover schema validity, stale baseline, forbidden changes, provenance tampering, split overlap, evaluator identity, exhausted reuse, evaluator failure consumption, crash no-resend, concurrent reservation limits, empty/noisy inputs and regressions.
